# Проверка батч-кода (`/proverka-batch-coda`): план, ревью, рефакторинг, где брать данные

Дата: 2026-11-17. Всё ниже проверено по коду репозитория и по живому проду (`deploy@45.135.234.8`, ветка `production`, коммит `6198dfc`). Внешние источники — со ссылками; где страница не открылась, это указано.

## 1. Короткий вывод

1. **Страница технически работает, но публично недоступна.** Новый стек живёт на `prod.mobiz.by` и закрыт basic-auth (страница отдаёт `401`), API при этом открыт (`/api/batch-code/brands` → `200`). Публичный `perfumer.by` до сих пор отдаёт старый OpenCart: `/proverka-batch-coda` → `404`. То есть функции «в интернете» пока нет.
2. **Данных мало и они не проверены.** 9 правил на 10 брендов; 8 из 10 брендов — «ориентировочно» по одному потребительскому гиду. Проверенных пар «код + напечатанная дата» — **0**. Заявок от покупателей в проде — **0**. Таблицы логов проверок (`batch_check_log`) нет, метрики из плана посчитать нечем.
3. **Цикл сбора данных не замкнут.** Заявки пишутся в `batch_code_submissions`, но страницы модерации в админке нет (только API). Данные, которые должны улучшать правила, никто не увидит.
4. **Главный дефект выдачи:** несколько кандидатов показываются как непрерывный период. Для `Dior 8A01` — «с январь 1998 по январь 2018», для `Estée Lauder 9A1` — «с октябрь 1991 по октябрь 2021». Это не диапазон выпуска, а две/четыре гипотезы; такую формулировку можно прочитать как ложное утверждение о товаре.
5. **План сам запрещал публичный запуск** до трёх условий (юрзаключение, ≥20 пар, измеренная точность). Ни одно не выполнено, а страница уже в `sitemap` и без `robots: noindex` — расхождение с решением «PILOT» из deep-research.
6. **Внешних готовых данных нет.** Ни у одного потребительского чекера нет API и права на перепубликацию; открытых датасетов с парами «код → дата» не существует. Легальные каналы: собственные пары (фото упаковок/стикеров), письменная лицензия у чекера, ответы производителей.
7. **Внутри БД пар нет.** На проде проверил: в складе, приходах, импортах и заказах нет полей партии, даты производства, срока годности или маркировки. `warehouse_stock_lots` — это «партия = остаток по цене», не заводской лот.

## 4. Ревью плана

**Что было верно**

- Отказ от скрейпинга и от чужого API — единственно законный путь; ресёрч это подтвердил.
- «Ориентировочная дата, не проверка подлинности» — правильная продуктовая рамка, она выдерживается в текстах.
- Разделение «формат распознан / даты нет / портал производителя» — честнее, чем у конкурентов.
- Модуль внутри Laravel, без отдельного сервиса — адекватно объёму.

**Что план не доработал**

1. **Не описал семантику нескольких кандидатов.** В API есть `date_from/date_to`, и это подтолкнуло фронт склеивать гипотезы в диапазон. План писал «Несколько вариантов: август 2017 или август 2007», но контракт ответа этому не соответствовал.
2. **Не сделал сбор данных обязательным этапом.** Пилот описан как «закрытая страница + конвейер пар», но конвейер (модерация, фото, согласие, метрики) не был специфицирован — в коде его и нет.
3. **Смешал зрелость правила и тип поддержки.** `approximate` — это и «уверенно декодируем», и «одна гипотеза из одного гида». Из-за этого нельзя отличить качественное правило от догадки, а `verified` недостижим.
4. **Отложил гейты «на потом».** Без `examples` и CI любое новое правило проходит ревью глазами; ошибка в `params` даёт 500 у пользователя, а не падение загрузки.
5. **Не назначил владельца данных.** Кто читает заявки, кто пишет производителям, кто переводит правило в `verified` — не зафиксировано; отсюда 0 заявок и 0 ответов.
6. **Решение PILOT не согласовано с релизом.** План: закрытый пилот без индексации. Факт: страница в проде и в sitemap. Это главное расхождение.

### 6.4. Маркировка ЕАЭС/РБ — важная поправка

Предыдущий отчёт утверждал, что духи в РБ не маркируются. Это устарело: парфюмерия входит в перечень товаров, маркируемых средствами идентификации (Постановление Совмина № 1030 от 27.12.2024; разъяснения МНС 2026 — [пример](https://www.dokshitsy.by/2026/06/realizaciya-produkcii-bez-dokumentov-i-kodov-markirovki-yavlyaetsya-narusheniem-zakonodatelstva/)). Плюс Решение Совета ЕЭК № 124 от 05.12.2025 (в силе с 28.02.2026) задаёт единые правила маркировки парфюмерно-косметической продукции ([pravo.by](https://pravo.by/document/?guid=11031&p0=F92500412&add)).

Но: публичная проверка кода маркировки не отдаёт дату производства; `productionDate` фигурирует в «Отчёте о производстве» (контур производителя), а у импорта на упаковке часто стикер импортёра с «годен до». Доступ к чужим кодам закрыт. Поэтому как **источник дат** маркировка сейчас не работает; как **источник пар для своих ввозимых товаров** — требует уточнения у оператора и юриста.

### 6.5. Ранжированные каналы

1. **Свои пары с упаковки** (фото дна/коробки, где видно и код, и напечатанную дату; стикер импортёра; recall-листы). Дорого по времени, зато законно и сразу пригодно как доказательство.
2. **Письменная лицензия у batchcodechecker.net / checkfresh.** Средние усилия, есть прямой путь в ToS.
3. **Письма группам** (Puig — Banderas/Rabanne/JPG; Coty — Burberry/CK/Gucci до 2027; Euroitalia — Versace/Moschino). Дёшево, ответ не гарантирован, но закрывает сразу пачку брендов.
4. **UGC-заявки покупателей** — только с согласием, без фото в открытом виде и с модерацией.
5. **Платный scentpulse** — максимум как «второе мнение» при ручной проверке, не в продакшене.

## 7. Пересмотренный план

### P0 — «сделать честно и измеримо» (1–2 дня, без миграций)

1. Многокандидатный вывод + грамматика (`batch-code-dates.ts`, форма). Плюс тест на `formatBatchCodePeriod`/описание кандидатов.
2. Сброс результата при смене бренда/кода; источники ссылками; `maxLength`; убрать «фото» из текста (или заменить на «пришлите фото письмом»).
3. Явный `robots: noindex` + убрать из sitemap — если пилот действительно закрытый (решение владельца).
4. Не показывать confidence, когда даты нет.

### P1 — «замкнуть сбор данных» (3–5 дней, нужны миграции и разрешение)

5. `batch_check_log` (brand, code_normalized, rule_id, rule_version, status, precision, created_at; без PII) + insert в `check()`. Это даёт метрики §5.3 и приоритизацию брендов.
6. `consent_at`, `consent_version`, `printed_date_precision` в заявках; запрет будущей `production`-даты; дедупликация `(brand_slug, code_normalized, printed_date, date_kind)`.
7. Админ-страница `/admin/batch-code` (список, фильтр по статусу/бренду, смена статуса, маскировка email) по образцу `frontend/src/app/admin/stock-notifications/page.tsx`; API-клиент по образцу `admin-reviews-api.ts`.
8. `examples` в JSON + data-driven тест (пример из каждого правила прогоняется через декодер) + проверка `params`, `valid_period`, `^…$`.
9. `is_active`/видимость витрины в `brands()` и `check()`; `display_brands` для Dior.

### P2 — «расширять покрытие» (недели, зависит от людей, не от кода)

10. Добавить Guerlain (300 товаров — самый крупный бренд каталога) тем же `lvmh_year_month`, если подтвердится источник; статус `approximate`, low/medium. Кандидаты: Moschino (Euroitalia), Bvlgari (нет правила — не переносить Dior).
11. Автодополнение по каталогу: переиспользовать `GET /api/brands` (без нового контракта), показывать «не поддерживается» и вести к заявке.
12. Письма производителям (только по решению владельца) и лицензия у чекера; пары → правило `verified` при N≥20 и ≥2 группах источников.
13. Отдельная таблица/реестр эталонов `batch_code_evidence` (код, дата, тип, источник, кто/когда ввёл) — чтобы заявки превращались в проверяемые пары, а не в свалку.

## 8. Топ-7 правок по соотношению «польза / дифф»

1. Многокандидатный вывод и грамматика — 1–2 файла, убирает главную ложную интерпретацию.
2. `batch_check_log` + `rule_version` — одна миграция + insert; без этого план не измеряется.
3. `consent_at` + `printed_date_precision` + запрет будущей production-даты — миграция + несколько строк.
4. Согласование нормализатора и regex (NBSP, `–—`, точка, `mb_strlen`).
5. `is_active` + видимость витрины в `brands()`/`check()`.
6. `examples` в JSON + data-driven тест + CI-скрипт.
7. `noindex` + удаление из sitemap (если пилот закрытый).

## 9. Что нужно решить владельцу

1. Публикуем страницу (cutover/снятие basic auth) или держим закрытый пилот? От этого зависят `robots`/sitemap и тексты.
2. Разрешаем ли миграции `batch_check_log` и поля согласия/точности? Без них метрики и юр. чистота недостижимы.
3. Добавляем ли Guerlain (300 товаров) на существующем декодере?
4. Кто владелец данных: кто читает заявки, кто пишет производителям, кто переводит правило в `verified`?
5. Отправляем ли письма Puig/Coty/Euroitalia/batchcodechecker (сейчас только черновики)?
6. Нужна ли фото-загрузка к заявке (ПДн, хранение) или достаточно «фото письмом»?

## 10. Можно ли спарсить базу батч-кодов (исследование 17.11.2026)

**Главное:** «базы код → дата» не существует ни у кого. У чекеров это не таблица, а декодер — функция на бренд. Проверено на Chanel в checkfresh: `6901 → 2021-10`, `0101 → 2024-02`, `9601 → 2024-01`; первые две цифры — месяц в 8-летнем цикле, вторые — счётчик внутри месяца. Информационное содержание кода — порядка 100 значений на бренд, а не тысячи.

**Что технически извлекаемо**

| Источник | Как | Ограничение |
| --- | --- | --- |
| checkfresh.com | серверный HTML: GET страницы бренда (~230 КБ, скрытые `marka_id`/`hash`) → POST → «Production date» | ToS: автоматический доступ и перепубликация запрещены |
| batchcodechecker.net | все 101 декодер лежат в публичном клиентском чанке (~62 КБ), один GET | ToS §2 (только personal), §4 прямо запрещает извлекать декодеры, §5 — код их собственность |
| lotdate.com | `GET api.lotdate.com/brands` отдаёт 3696 брендов без авторизации | само декодирование закрыто Cloudflare Turnstile |
| scentpulse | платный API, $0.10/вызов, 5 домов (Chanel, Dior, Tom Ford, Gucci, YSL) | оплата USDC on Base; ToS запрещает перепродажу raw data как датасета |
| cosmeticsbatch.com | — | Cloudflare 403, ToS даже не прочитать |

**Юридически.** Даты — это факты, они не охраняются (ст. 14 Закона РБ № 262-З; своего sui generis в РБ нет, в отличие от Директивы ЕС 96/9). Но запреты в ToS — это договор: C-30/14 подтверждает, что они действуют, даже если база не защищена. Практические рычаги операторов — C&D, жалоба хостеру/Cloudflare, блокировка рекламных аккаунтов, репутация у поставщиков и брендов. Судиться в Беларуси по польской/иностранной подсудности невыгодно, но письмо с требованием — дешёвый шаг.

**Градация риска:** ручная проверка «вторым мнением» — низкий; разовый парс и хранение у себя — средний (нарушение ToS, ценность низкая); парс + показ пользователям — высокий (перепубликация); лицензия/платный API — минимальный.

**Открытые данные не помогут:** Open Beauty Facts — 80 682 товара (≈455 парфюма), но в схеме нет `lot/batch/production_date` (168 ключей карточки, 191 колонка CSV), а слоты фото только `front/ingredients/packaging` — батч-код структурно некуда положить. Wikimedia/Wikidata — 0. GitHub — ни одного декодера с лицензией. openFDA/CPSC/Safety Gate — нет поля «лот + дата производства» для наших брендов.

**Рекомендация.** Строить не «базу кодов», а базу правил + собственные пары «код → дата» (фото упаковки/стикера импортёра, документы прихода). Для быстрого расширения: письмо с запросом лицензии в `contact@batchcodechecker.net` и `support@checkfresh.com`; scentpulse — только как точечный платный источник по 5 домам. Массовый парсинг не окупается: ценность в ~100 строках логики на бренд, а не в выгрузке.
